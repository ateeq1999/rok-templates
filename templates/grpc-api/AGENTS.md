# AGENTS.md

One crate, folders by feature, a fixed set of files per feature, six rules:
the axum template's, served over gRPC. Humans and code generators follow
this file exactly. If a rule gets in your way, change the rule here first,
then the code.

`rok sqlc g` generates the data layer (`src/db/`), one API feature per
table (`src/features/<table>/`, a tonic service) and its `.proto`
(`proto/<table>.proto`) from `schema/`. Generated files start with
`// @generated by rok-data-sqlc` and are rewritten on every run: never edit
them. Scaffolded files start with `// Scaffolded once by rok-data-sqlc` and
are yours.

## Layout

```
build.rs          compiles proto/ with protox (no protoc) into messages,
                  servers and clients, and the descriptors reflection serves
proto/            generated <table>.proto files; add your own beside them
src/
├─ lib.rs         declares every module `pub`: the application is a library
├─ main.rs        starts the server through the library. Nothing else.
├─ app/           the ONLY wiring: state.rs (AppState), routes.rs (the
│                 services, health and reflection), auth.rs (the caller
│                 check in front of the API), run.rs (the server and what
│                 runs beside it)
├─ config.rs      reads env vars into one Config (the ONLY env reader)
├─ error.rs       AppError, which shared/grpc.rs turns into a gRPC status
├─ db/            generated data layer: rows, typed ids, enums, all SQL, pool.rs
├─ shared/        tools with no business meaning (auth.rs, security/, mail/,
│                 jobs/, storage/ are yours; grpc, response, pagination,
│                 validation are generated)
└─ features/
   ├─ mod.rs        `mod generated; pub use generated::*;` plus hand-written features
   ├─ generated.rs  generated: declares the features, includes the compiled
   │                package (`proto`) and holds `routes`
   └─ <feature>/
      ├─ mod.rs          generated: re-exports the service and the trait
      ├─ grpc.rs         generated: read the message, call one service method, answer
      ├─ dto.rs          generated: the inputs and their validation
      ├─ model.rs        generated: re-exports the rows and typed ids from db
      ├─ repo.rs         generated: re-exports the table's db functions
      ├─ service_api.rs  generated: the service trait, with a default per RPC
      └─ service.rs      yours: the service struct and your overrides (business rules)
```

No other file may be added to a feature, and no file or directory anywhere
under `src/` may be named `utils`, `helpers` or `common`.

## Where does each piece of code go?

| I am writing... | It goes in | Never in |
|---|---|---|
| A business rule | the feature's `service.rs`, overriding a `service_api.rs` default | `grpc.rs`, repo |
| A new RPC on a Resource, or a field | the schema and `rok-data-sqlc.toml` (`[api]`), then `rok sqlc g` | generated files |
| An RPC of your own | a hand-written `proto/<name>.proto` importing the generated messages, its service in a hand-written feature, added in `app/routes.rs` | the generated `.proto` |
| SQL query | the truth in `schema/` and `rok sqlc g`, or `queries/<feature>.sql` | service, `grpc.rs` |
| New DB table or column | `schema/000N_name.sql`, then `rok sqlc g` | anywhere else |
| Error case | a variant in `error.rs` | feature folder |
| Who is calling | `app/auth.rs` puts the `AuthUser` in the request's extensions | a service |
| Env variable | `config.rs` | `std::env` anywhere else |
| Background or slow work | a job (`shared/jobs/`), registered in `app/run.rs` | request path |

## The six rules

1. In a feature, only `grpc.rs` uses `tonic`. Outside the features, so may
   `app/`, `main.rs`, the features' `generated.rs`, `shared/` and the data
   layer.
2. In a feature, only `repo.rs` and `model.rs` use `sqlx`, and `service.rs`
   and `service_api.rs` may name `sqlx::PgPool` and `sqlx::PgConnection`
   and nothing else.
3. `service.rs` never writes SQL. It calls the data layer's functions and
   traits from `shared/`.
4. A feature never refers to another feature's modules.
5. `shared/` never refers to the features.
6. No `unwrap()`, `expect()`, `panic!`, `todo!`, `println!` or `dbg!`. Every
   fallible function returns `Result<_, AppError>`.

## Shared with the axum template

`config.rs`, `migrations/`, `schema/`, `queries/`, `shared/jobs/`,
`shared/mail/`, `shared/storage/`, `shared/security/`, `telemetry.rs`,
`metrics.rs`, `settings.rs`, `shutdown.rs` and the data layer's
`queries/`, `pool.rs`, `nullable.rs` and `schema.rs` are the axum
template's, file for file. A fix to one belongs in both.

## Checks

`cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`,
`cargo test` and `rok sqlc g --check`.
